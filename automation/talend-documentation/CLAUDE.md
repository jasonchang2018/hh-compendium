# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

See [README.md](README.md) for the full description, usage, and quick start. In short: a multi-stage CLI toolkit that reverse-engineers documentation for an undocumented Qlik Cloud + Talend Studio data platform. It never touches production data — only implementation metadata (job definitions, load scripts, schemas, connection targets) — and redacts anything that looks like a credential.

Independent, standalone scripts run in sequence, each living under `src/` in its own subfolder, grouped by source system (`talend/`, `qlik/`, `documentation/`), plus two optional stages (AI enrichment, publish):

1. `src/talend/talend_extractor.py` — Talend Studio workspace directory, project archive (`.zip`), **or a git repo URL** → `talend_metadata.json` + `extraction-report.json`.
2. `src/qlik/qlik_cloud_extractor.py` — Qlik Cloud REST API → `qlik_metadata.json`.
3. `src/documentation/generate_documentation.py` — Markdown skeleton + `AI_DOCUMENTATION_PROMPT.md` for external (manual) AI enrichment.
4. `src/documentation/enrich_documentation.py` — deterministic (no AI) architecture/job/lineage/runbook/dependency-matrix docs.
5. `src/documentation/ai_enrich_documentation.py` (optional, opt-in via `AI_ENRICHMENT_ENABLED`) — automates what stage 3's `AI_DOCUMENTATION_PROMPT.md` otherwise asks a human/agent to do by hand: calls Claude via the `anthropic` SDK, one API call per document (per Talend job, per Qlik app, and once each for the four system-level docs), and overwrites those documents in place. Must run after stages 3 and 4 (it reads their output as ground-truth input, not from JSON alone) and before stage 6. Uses `src/documentation/llm_client.py` (a small local provider abstraction, not shared outside `src/documentation/`) and `config/llm.yaml` for model/temperature/max-tokens settings — the one deliberate exception to this repo's "env vars only, no YAML config" convention, since it mirrors `talend-doc-gen/enrichment`'s config style at the repo owner's request. The API key itself is still env-var only (`ANTHROPIC_API_KEY`), never in the YAML file.
6. `src/documentation/export_docx.py` — Markdown → Word (`.docx`), Mermaid diagrams rendered and embedded as images.
7. `src/documentation/publish_docs.py` (optional) — publishes the final `documentation/` tree to a separate docs git repo; not an extractor, an opt-in publish stage that runs after the rest of the pipeline.

There is no shared library code between the scripts by design — each is self-contained and runnable on its own (see the `git_repo.py` duplication note below for how this plays out for the two newest scripts). Future scripts (e.g. Talend Management Console integration) should land under `src/` in their own appropriately named subfolder, following the same pattern.

## Commands

See README.md's Quick Start for full usage and every CLI flag/env var. Dependency management is via `uv` (`uv sync`). Run `uv run ruff check .` before committing; no formatter is configured. Self-check tests (`src/talend/test_mode_b.py`, `src/talend/test_mode_c.py`, `src/documentation/test_enrich_documentation.py`, `src/documentation/test_ai_enrich_documentation.py`, `src/documentation/test_export_docx.py`, `src/documentation/test_publish_docs.py`) are plain `assert`-based scripts run directly via `uv run <path>` — this repo has no test framework (no pytest). `test_ai_enrich_documentation.py` makes no real Anthropic API calls (a fake `LLMProvider` stub stands in); only its disabled-by-default and `--dry-run` paths are exercised end to end via subprocess, since neither needs `ANTHROPIC_API_KEY`.

## Architecture notes worth knowing before editing

- **Redaction is name-based, not value-based**, and duplicated independently in each extractor: `talend_extractor.py` has `SENSITIVE_PARAM_NAMES`/`is_sensitive_param`/`sanitize_value`; `qlik_cloud_extractor.py` has `SENSITIVE_CONN_PROPS`/`sanitize_connection` plus a value-regex scan for inline credential tokens (Qlik only). A parameter/property is redacted if its _name_ substring-matches a known credential keyword — values are never inspected (except Qlik's regex pass). If you add a new field that could carry a secret, add its name pattern to the relevant set in both places if applicable. Git remote URLs/tokens are a separate redaction concern, handled by `redact_repo_url()` in both `git_repo.py` files (masks embedded userinfo/token in a URL, e.g. before logging or writing `extraction-report.json`) — a different data category from job/connection parameters, so it isn't merged into `SENSITIVE_PARAM_NAMES`/`SENSITIVE_CONN_PROPS`.
- **`git_repo.py` is intentionally duplicated, not shared**: `src/talend/git_repo.py` (used by `talend_extractor.py`'s Mode C) and `src/documentation/git_repo.py` (used by `publish_docs.py`) implement the same clone/fetch/auth-resolution logic almost verbatim — the documentation twin additionally has `commit_and_push` since only the publish stage needs to push. This mirrors the existing precedent of duplicating the redaction sets between `talend_extractor.py` and `qlik_cloud_extractor.py` above: it keeps each script fully standalone with no shared library import between `src/talend/` and `src/documentation/`, at the cost of keeping the two files in sync by hand when one changes.
- **`generate_documentation.py` and `enrich_documentation.py` have zero network/filesystem-extraction logic** — they only consume the JSON produced by the two extractors and format Markdown/Mermaid via plain string building (no templating engine anywhere in this repo). If you need new source data, add it to the extractor's JSON output first. `ai_enrich_documentation.py` is the one exception with network logic in `src/documentation/` — it calls the Anthropic API, and deliberately runs after both of the above (it reads their Markdown output as ground truth, not the raw JSON alone).
- **`ai_enrich_documentation.py` intentionally overwrites the same 01/04/05/06 filenames `enrich_documentation.py` writes deterministically**, plus the per-job/per-app files `generate_documentation.py` writes — this is not a naming collision to resolve, it's the designed hand-off: when `AI_ENRICHMENT_ENABLED=true`, Step 5's deterministic output becomes ground-truth *input* to this stage, and its Claude response becomes the new file content. If the expected file doesn't exist yet (Steps 4/5 haven't run), it fails loudly on that document rather than trying to synthesize one from JSON alone — that logic already lives in `generate_documentation.py`/`enrich_documentation.py` and shouldn't be duplicated here. Its own JSON→document sanitization (`sanitize_payload`, allow-list + deny-list) is a second, independent scrub applied on top of — not instead of — `SENSITIVE_PARAM_NAMES`/`SENSITIVE_CONN_PROPS`, specifically because this is the one point in the pipeline where metadata leaves the local environment for a third-party API.
- **Talend job parsing is tolerant, not strict**: `parse_component`, `parse_connection`, `parse_schema_columns`, `parse_job_properties` use `safe_get`-with-defaults and try both direct attributes and nested elements, to survive Talend Studio version differences. Follow the same pattern when extending — a parse failure should degrade (return `None`/skip/log a warning), never crash the whole run.
- **Talend Mode B (archive input)** unpacks the `.zip` into `<working-dir>/<archive-stem>/` (overwriting reruns) and hands that directory to the _same_ `find_projects`/`extract_project`/`extract_workspace` code Mode A uses — no parsing-logic fork between modes. **Mode C (git-repo input)** works the same way: `is_git_url()` detects a git URL passed as the `workspace` argument, `clone_or_update_repo()` clones it (or fetches + hard-resets an existing clone) into `<working-dir>/<repo-slug>/`, and that directory is handed to the same `extract_workspace()` code — still no parsing-logic fork. Every run (Mode A, B, or C) writes `extraction-report.json`: archive checksum (`null` outside Mode B), `repo_url`/`branch`/`commit_sha` (`null` outside Mode C), per-job status (`SUCCESS`/`PARTIAL`/`FAILED`/`SKIPPED_DUPLICATE`, derived by attaching a temporary `logging.Handler` around each job's parse), and unsupported-artifact folders from a fixed, documented list (`UNSUPPORTED_ARTIFACT_FOLDERS`) — not a heuristic scan.
- **`export_docx.py` hand-rolls Markdown parsing** (no new dependency) rather than adding a Markdown library — scoped to what this repo's own generators (plus AI output in the same idiom) actually produce: headings, lists, GFM tables, fenced code blocks, `**bold**`/`` `code` `` spans, blockquotes. Mermaid blocks render via `mermaidx` straight to an in-memory `io.BytesIO` → `add_picture()`; no temp files ever touch disk. Must run last, after any AI-authored Markdown has been saved back into `documentation/` — whether by the manual workflow or by `ai_enrich_documentation.py`. If `publish_docs.py` is also used, it must run after `export_docx.py` too, since it publishes the `docx/` subtree along with the Markdown.
- Both extractors write JSON directly via `dataclasses` → `asdict()`; no templating engine is used anywhere in the repo.
- `.env`, `talend_metadata.json`, `qlik_metadata.json`, `documentation/`, and `full-documentation/` are all gitignored — don't force-add the generated ones. (`src/documentation/*.py` and `src/talend/*.py` source files _are_ tracked despite living under a `documentation`-named path; a broad `documentation/` gitignore pattern means new files there need `git add -f`.)
- Qlik load-script table extraction is best-effort regex (`extract_tables_from_script`), not a real parser — treat its output as an AI hint, not ground truth.
